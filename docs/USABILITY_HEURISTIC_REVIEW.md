# USABILITY_HEURISTIC_REVIEW.md

> 검토일: 2026-09-26 · 대상: 현재 작업 트리(우리몫 MVP) — 전체 7화면(S1~S7) + 탭 3종(자산 목록/정산 현황/설정)
> 방법: 코드 전수 검토 + `pnpm install` 후 Next.js dev 서버를 별도 환경에 재현, Playwright로 실제 조작(자산 생성 2건·균등/납부액 두 분배 방식, 비용 추가/삭제, 종료→정산→요약 전체 흐름, 탭 3종 이동, 존재하지 않는 자산 URL 직접 접근, 경계값 입력 등)한 관찰 결과를 근거로 작성. 기준은 Jakob Nielsen의 사용성 휴리스틱 10원칙.

## 요약

접근성 기본기(터치 타깃 44px 이상, 포커스 링, `role="alert"`, `aria-current`, 라벨-입력 연결)와 오류 메시지의 구체성은 4주 MVP치고 상당히 탄탄하다. 반면 **핵심 도메인 규칙(납부액 합계 검증)이 화면마다 다른 기준으로 적용되고 있어, 개별 참여자에게 음수 지분이 계산돼도 "합계 일치" 성공 배지가 뜨는 사례를 실제로 재현했다.** 이 건이 이번 검토에서 가장 우선순위가 높다. 그 외에는 드릴다운 화면의 이탈 경로 부족, 금액 입력 필드의 사소한 마찰 등 중간~낮은 우선순위 항목들이다.

## 원칙별 평가

### 1. 시스템 상태의 가시성
- (+) 지분율·정산액 옆에 계산식을 항상 함께 노출한다(`FormulaText`, 예: "1,300,000 ÷ 900,000"). 결과만 보여주지 않고 근거를 보여줘 신뢰도를 높인다.
- (+) 저장 관련 상태(로컬 저장 실패, 데이터 없음)를 배너로 알린다(`Banner`, `saveError`/`loadError`).
- (-) **자산 목록(S1)에는 "납부액 합계 불일치" 같은 데이터 이상 상태를 알려주는 표시가 전혀 없다.** 같은 정보를 "정산 현황" 탭에서는 "납부액 확인 필요" 배지로 보여주면서(`src/app/app/settlements/page.tsx`), 정작 가장 먼저 보는 목록 화면(S1, `src/app/app/page.tsx`)에는 아무 표시가 없어 문제가 있는 자산을 눈으로 구분할 수 없다.

### 2. 시스템과 실제 세계의 일치
- (+) "납부액", "지분율", "매각가", "합의 메모" 등 실제 룸메이트/동아리 공동구매 맥락에 맞는 용어를 사용한다. 비용 유형(수리비/추가 구매비/배송비)도 실사용 시나리오에 부합한다.
- (+) 비용 기록 날짜 입력 기본값을 오늘 날짜로 채워줘(`CostForm.tsx`) 불필요한 입력을 줄인다.
- 특이사항 없음(양호).

### 3. 사용자 제어와 자유
- (+) 자산 상세(S3)에는 "자산 목록으로 나가기" 이탈 링크가 있다.
- (-) **비용 기록(S4)·종료 규칙(S5)·정산(S6)·공유 요약(S7) 4개 드릴다운 화면에는 이 이탈 링크도, 탭바도 없다.** 헤더의 ← 버튼으로 한 단계씩만 되돌아갈 수 있어, 예를 들어 정산 화면(S6)에서 자산 목록으로 가려면 종료 규칙(S5) → 상세(S3) → 목록 순으로 3번 이동해야 한다. `CLAUDE.md`의 세션6 메모는 "드릴다운 화면 전체에 뒤로가기+이탈 링크가 있다"고 적고 있으나 실제 코드는 S3에만 이탈 링크가 있어 문서와 구현이 어긋나 있다.
- (+) 참여자 최소 인원(2명) 미만으로는 삭제 버튼이 비활성화돼(`removeMember`, `disabled={members.length <= 2}`) 실수로 조건을 깨는 것을 막는다.

### 4. 일관성과 표준
- (+) 버튼 높이(`min-h-11`=44px), 카드 모서리(`rounded-2xl`/`rounded-xl`), 포커스 링(`focus:ring-2`) 등 컴포넌트 스타일이 화면 전반에 일관적이다.
- (+) 아이콘 전용 액션을 지양하고 텍스트 라벨을 쓰는 원칙이 대체로 지켜진다(예: 삭제 버튼에 "삭제" 텍스트, `AppHeader`의 뒤로가기만 의도적 예외로 문서화됨).
- (-) 자산 이름을 보여주는 두 목록 화면의 스타일이 다르다: "정산 현황" 탭(`src/app/app/settlements/page.tsx`)의 `<h2>`에는 `truncate`가 적용돼 긴 이름이 잘리지만, "자산 목록"(S1, `src/app/app/page.tsx`)의 동일한 `<h2>`에는 `truncate`가 없어 긴 물건명이 삭제 버튼과 줄바꿈으로 부딪힐 수 있다.

### 5. 오류 예방 — **이번 검토 최우선 항목**
- (-) **참여자 개별 납부액에 음수를 입력해도 자산을 만들 수 있고, 지분율도 음수로 계산돼 저장된다.** 재현: 총 구매금액 900,000 / 참여자 A 납부액 1,300,000 / 참여자 B 납부액 -400,000 → 합계가 900,000으로 맞아떨어지므로 "✓ 납부액 합계가 총 구매금액과 일치합니다" 배지가 뜨고, 지분 미리보기에는 "B: -44.4% (-400,000 ÷ 900,000)"가 그대로 표시되며 제출 버튼도 활성 상태다. 원인은 `checkContribution`(`src/lib/calc/shares.ts:6`)과 폼의 `contributionSumOk`(`src/app/app/assets/new/page.tsx:83`)가 합계만 검사하고 개별 값의 부호를 검사하지 않기 때문. 실제 소유 지분이 음수가 되는 것은 이 서비스의 핵심 불변식을 깨는 상태인데도 성공으로 표시된다.
- (-) **납부액 합계가 총 구매금액과 정확히 일치하지 않아도 자산 생성 자체는 막히지 않는다.** 폼의 제출 가능 조건(`contributionSumOk = splitMode === "equal" || contributionCheck.sum > 0`, `src/app/app/assets/new/page.tsx:83`)은 "0보다 큼"만 확인하고, 실제 일치 여부(`checkContribution(asset).ok`)는 확인하지 않는다. 반면 종료·정산 진입은 `contributionCheck.ok`를 기준으로 막는다(`src/app/app/assets/[id]/page.tsx:131`). 즉 생성 단계와 이후 단계가 서로 다른 검증 기준을 쓰고 있어, 사용자는 경고 배지를 보고도 일단 만든 뒤 나중에 상세 화면에서 다시 고쳐야 하는 이중 작업을 겪는다.
- (+) 삭제·전체 초기화 등 되돌릴 수 없는 동작에는 예외 없이 `window.confirm` 확인과 "되돌릴 수 없습니다" 문구가 붙어 있다.
- (+) 비용 금액은 `amount > 0`을 명시적으로 검사해 0원·음수 비용은 등록되지 않는다(`CostForm.tsx`) — 위 참여자 납부액 케이스와 대비된다.

### 6. 기억보다는 인지
- (+) 관리자 지정, 비용 부담자 선택 등을 항상 드롭다운으로 제공해 참여자 이름을 다시 타이핑할 필요가 없다.
- (+) 제출 불가 상태일 때 "물건명, 총 구매금액(0보다 큼), 참여자 2명 이상…을 입력하면 만들 수 있어요" 같은 조건 안내 문구가 버튼 바로 아래 노출된다(`src/app/app/assets/new/page.tsx:287`).

### 7. 사용의 유연성과 효율성
- (-) 자산 생성 후에는 참여자를 추가·삭제하거나 이름을 고칠 방법이 없다. 관리자 재지정만 가능하고, 나머지 참여자 구성은 생성 폼에서만 편집할 수 있다. "나중에 한 명이 빠지거나 새로 들어오는" 흔한 상황에 대응하려면 자산을 처음부터 다시 만드는 것 외엔 방법이 없다.
- 그 외에는 MVP 범위(결제·인증·실시간 협업 제외, `CLAUDE.md` Boundaries)에 맞게 단순한 단일 경로로 설계돼 있어 큰 비효율은 없다.

### 8. 심미적이고 미니멀한 디자인
- (+) 설정 탭이 버튼 하나로 휑하지 않도록 데이터 현황 카드 + 5단계 이용 가이드를 추가한 것은 "빈 화면"과 "불필요한 장식" 사이 균형을 잘 잡은 선택이다.
- (+) 색상 대비를 계산해보면 본문 텍스트(`#0f172a`/`#ffffff`) 17.9:1, 보조 텍스트(`#5b6478`/`#ffffff`) 5.9:1, 경고·성공 배지 색상 조합 모두 4.8:1 이상으로 WCAG AA(4.5:1) 기준을 충족한다.

### 9. 오류 인식, 진단, 복구 지원
- (+) 이 서비스에서 가장 잘 만든 부분. 존재하지 않는 자산 URL 직접 접근 시 "해당 자산을 찾을 수 없어요 / 목록으로 돌아가기"를, 납부액 불일치 시 "총 구매금액보다 OOO원 많습니다/적습니다 (현재 합계 OOO원)"처럼 원인과 현재 값을 함께 보여주고, 종료·정산 진입이 막힐 때도 "자산 상세에서 납부액 확인하기" 링크로 바로 이동시켜 준다.
- (+) 정산 결과 합계 검증(`checkOk`)이 실패하는 경우까지 별도 오류 문구를 준비해 두어, 반올림 등으로 계산이 어긋나는 극단적 상황도 침묵하지 않고 알린다.

### 10. 도움말 및 문서
- (+) 설정 탭의 "우리몫 이용 방법" 5단계 가이드가 별도 도움말 화면 없이도 전체 흐름(등록→지분 확인→비용 기록→종료 규칙→정산)을 한눈에 보여준다.
- (-) 개별 화면 안에는 보조 설명이 거의 없다. 예를 들어 지분 미리보기의 계산식(`1,300,000 ÷ 900,000`)이나 "왜 종료·정산이 막혀 있는지"는 문구로는 설명되지만, 처음 쓰는 사용자 입장에서 "왜 납부액 합계가 정확히 맞아야 하는지" 같은 배경 설명은 어디에도 없다. 우선순위는 낮음 — 지금 수준의 문구만으로도 MVP 데모에는 충분하다.

## 결론

전반적으로 접근성·오류 메시지·시각적 일관성 등 "만듦새" 관련 원칙은 잘 지켜지고 있고, 4주 MVP 범위 대비 완성도가 높다. 다만 이 서비스의 존재 이유인 "지분·정산 계산의 정확성" 쪽에서 검증 로직이 화면마다 다른 기준을 쓰고 있어, 음수 납부액처럼 명백히 잘못된 입력도 성공으로 표시되는 사례가 실제로 재현됐다. 다음 작업 회차에는 표의 "높음" 두 항목(개별 납부액 부호 검증, 생성 단계 검증 기준 통일)을 최우선으로 다루는 것을 권장한다.
