# UX_IMPROVEMENT_PROPOSAL.md

> 작성일: 2026-09-26 · 근거: `docs/USABILITY_HEURISTIC_REVIEW.md`(닐슨 10원칙 자가검진)에서 도출된 개선 항목 6건
> 방법: 같은 도메인(정산·더치페이·공동비용 관리) 서비스 3곳 — Splitwise(글로벌 정산 앱), 카카오페이 정산하기(더치페이), 토스(국내 핀테크 입력 UX 표준) — 의 실제 UX 패턴을 조사해 우리몫에 적용 가능한 형태로 재구성. 우리몫은 "로컬 저장·단일 기기·서버 없음"(`CLAUDE.md` Boundaries)이라는 제약이 있어, 레퍼런스 서비스의 서버·멀티유저 전제가 깔린 기능은 그대로 가져오지 않고 이 제약에 맞게 걸러서 반영했다.

## 레퍼런스 요약

| 서비스 | 왜 참고하나 | 우리몫과 다른 전제 |
|---|---|---|
| [Splitwise](https://www.splitwise.com/) | 지분·정산 계산 도메인이 거의 동일한 글로벌 대표 서비스. 그룹 멤버 관리·잔액 검증 UX 참고 | 서버 동기화 기반 멀티유저 앱 — 우리몫은 로컬 단일 기기 |
| 카카오페이 정산하기(더치페이) | 국내 사용자에게 가장 익숙한 1/N vs 직접입력 분배 UX, 참여자 관리 UX | 카카오톡 인증·송금 연동 — 우리몫은 결제·인증 없음(Boundaries) |
| 토스 | 국내 핀테크 입력 필드·폼 검증 UX의 사실상 표준(오류를 보여주기보다 애초에 못 만들게 막는 설계 철학) | 해당 없음(설계 철학만 차용) |

## 개선안

### 1. [높음] 금액 입력 필드에서 음수를 아예 입력하지 못하게 막기
- **문제**(USABILITY_HEURISTIC_REVIEW.md #5): 참여자 납부액에 음수를 넣어도 합계만 맞으면 통과되고, 지분이 음수(-44.4%)로 계산돼 저장된다.
- **레퍼런스**: 토스는 "유효성 검사 후 에러를 보여주는" 방식 대신 "포맷에 따라 입력 자체를 제어"하는 쪽을 원칙으로 삼는다([「거꾸로 입력하는 가입 화면, 처음에 어떻게 떠올렸을까?」](https://toss.tech/article/toss-signup-process)) — 잘못된 값이 아예 만들어지지 않게 막는 것이 사후 경고보다 우선한다는 설계 철학이다. 국내 금융 앱들이 금액 입력란에서 `-` 키 자체를 받지 않는 것도 같은 맥락.
- **적용**: `src/components/NumberInput.tsx`의 `onChange`에서 `-` 문자를 정규식으로 걸러내거나(`raw.replace(/[^0-9]/g, "")`), 최종값을 `Math.max(0, Number(raw))`로 클램프. `type="number"` + `min={0}`만으로는 타이핑 자체를 막지 못한다는 걸 이번 검진에서 직접 확인했으므로, HTML 속성이 아니라 JS 레벨에서 막아야 한다.

### 2. [높음] "지분 미리보기"를 Splitwise식 "남은 금액" 라이브 카운터로 바꾸고, 생성 단계 검증을 종료 단계와 통일
- **문제**(#5): 생성 폼은 납부액 합계가 총액과 달라도(`contributionSumOk`가 `sum > 0`만 확인) 제출이 가능한데, 종료·정산 단계는 정확히 일치해야만 진행된다. 기준이 서로 달라 사용자가 "일단 만들고 나중에 다시 고치는" 이중 작업을 겪는다.
- **레퍼런스**: Splitwise의 "금액으로 나누기" 화면은 참여자별 금액을 입력하는 동안 총액과의 차액을 실시간으로 계산해 보여주고, 0이 되기 전까지는 저장을 막는 방식으로 설계돼 있다. 카카오페이 정산하기도 "1/N이 애매하면 개별 금액을 직접 입력"할 수 있게 하되([관련 기사](https://www.seoulfn.com/news/articleView.html?idxno=397440)), 합계가 안 맞는 채로 다음 단계로 넘어가는 것은 허용하지 않는다 — 두 서비스 모두 "분배 방식은 자유롭게, 그러나 합계 불일치 상태로의 진행은 불허"라는 원칙을 공유한다.
- **적용**:
  - `checkContribution`(`src/lib/calc/shares.ts:6`)의 `ok` 기준을 생성 폼의 `contributionSumOk`(`src/app/app/assets/new/page.tsx:83`)에도 동일하게 적용해 두 화면의 검증 기준을 하나로 통일.
  - "지분 미리보기" 박스의 `ContributionCheckBadge` 옆에 "남은 금액: OOO원" 한 줄을 추가(이미 `check.diff` 값이 계산돼 있으므로 표시만 추가하면 됨). 0원이 되면 초록 배지로 바뀌고, 아니면 빨간 숫자가 실시간으로 남아 있어 피드백이 즉각적이다.
  - 이 두 가지를 합치면 "자산 만들기" 버튼이 비활성화된 이유를 지분 미리보기 숫자만 보고도 바로 이해할 수 있게 된다.

### 3. [중간] 드릴다운 화면에 "닫기(X)" 상시 노출 — 뒤로가기와 역할 분리
- **문제**(#3): 비용 기록·종료 규칙·정산·공유 요약(S4~S7) 화면에는 헤더의 ← 버튼(한 단계씩 이동)만 있고, 자산 목록으로 바로 나가는 경로가 없다. 정산(S6)에서 목록으로 가려면 최소 3번 이동해야 한다.
- **레퍼런스**: 결제·가입·예약처럼 여러 단계를 거치는 국내 앱 플로우(토스 결제, 카카오T 예약, 배달의민족 주문 등)는 예외 없이 "뒤로가기(←)"와 "완전히 나가기(X)"를 헤더에 분리해서 함께 배치한다. ← 는 직전 단계로, X는 플로우 전체를 벗어나는 용도로 역할이 다르다.
- **적용**: `AppHeader`(`src/components/AppHeader.tsx`)의 오른쪽 44px 슬롯(현재 빈 `<span aria-hidden="true" />`)에 `closeHref` prop을 추가해 X 버튼을 넣고, S4~S7 4개 화면에 `closeHref="/app"`을 전달. 여유가 되면 같은 자리에 "2/4"처럼 남은 단계 표시도 함께 넣을 수 있다(작은 추가라 이번 항목에 묶어 처리 가능).

### 4. [중간] 자산 생성 후 참여자 추가·삭제 지원 (Splitwise의 "잔액 0 아니면 삭제 금지" 가드레일 포함)
- **문제**(#7): 자산을 만든 뒤에는 참여자를 추가·삭제하거나 이름을 고칠 방법이 없다. "한 명이 나중에 빠지거나 새로 들어오는" 흔한 상황에 대응이 안 된다.
- **레퍼런스**: Splitwise는 그룹 멤버를 언제든 추가·삭제할 수 있게 열어두되, [잔액(balance)이 남아있는 멤버는 삭제를 막고 "먼저 잔액을 정리해 달라"는 안내와 함께 정산 방법(현금 결제 기록 또는 관련 비용에서 제거)을 제시한다](https://kb.splitwise.com/groups/how-do-i-remove-a-person-from-a-group). "언제든 편집 가능하되, 돈이 걸린 상태에서 사람을 지우는 것만은 막는다"는 원칙이다.
- **적용**: 자산 상세(S3, `src/app/app/assets/[id]/page.tsx`)에 참여자 추가·삭제 섹션 추가.
  - 추가: 새 참여자는 납부액 0으로 시작(납부액 모드) 또는 균등분할 재계산(균등 모드) — `computeShares`를 그대로 재사용할 수 있어 계산 로직 변경은 불필요.
  - 삭제: 해당 참여자가 낸 비용(`asset.costs`에 `payerId`로 매칭되는 항목)이 있거나 이미 `salePrice`가 입력돼 정산이 진행 중이면 삭제를 막고 "비용을 다른 참여자에게 재배정하거나, 정산 시작 전에 삭제해 주세요"로 안내.
  - 참고: 우리몫은 Splitwise와 달리 서버 동기화가 없는 단일 기기·단일 운영자 구조라 "다른 사람이 실수로 지우는" 문제 자체가 없다. 따라서 Splitwise의 권한 분리 로직까지는 가져올 필요 없이, "삭제 조건" 가드레일만 채택하면 된다.

### 5. [낮음] 금액 입력 필드를 지우면 빈칸으로 유지 (0으로 스냅되지 않게)
- **문제**(#1/#9): `NumberInput`을 지우면 빈칸이 아니라 강제로 "0"이 되어(`src/components/NumberInput.tsx:21-24`), 재입력할 때 "0"부터 지우고 새로 타이핑해야 하는 사소한 마찰이 있다.
- **레퍼런스**: 국내 금융 앱의 금액 입력 필드는 "입력 중(빈칸)"과 "값이 채워진 상태"를 명확히 구분해서 다룬다 — 빈칸일 때는 자리표시자(placeholder)만 보이고, 지우면 그냥 빈칸으로 돌아간다. 토스의 "예측 가능한 상태 전환" 설계 철학과 같은 맥락([참고](https://toss.tech/article/toss-signup-process)).
- **적용**: `NumberInput`의 `onChange`가 빈 문자열을 0으로 바꾸지 않도록 수정(`value: number | ""` 타입은 그대로 두고, 빈 값일 때는 상위 state에 `""`를 그대로 전달). 숫자 변환은 제출 시점에만 하면 되므로 나머지 계산 로직은 그대로 둬도 된다.

### 6. [낮음] 자산 목록(S1)에도 정산 현황 배지 재사용 + 긴 이름 truncate 통일
- **문제**(#4): "정산 현황" 탭에만 "납부액 확인 필요/정산 완료/정산 전" 배지가 있고, 정작 가장 먼저 보는 자산 목록(S1)에는 아무 표시가 없다. 물건명 truncate 처리도 두 화면이 다르다.
- **레퍼런스**: 카카오페이 정산 현황 리스트는 어느 화면에서 봐도 "조치가 필요한 항목"이 같은 배지로 표시된다 — 목록 화면마다 상태 표시 기준이 달라지지 않는다.
- **적용**: `src/app/app/settlements/page.tsx`의 배지 JSX(43~55행)를 `StatusBadge` 같은 작은 공용 컴포넌트로 추출해 `src/app/app/page.tsx`(S1) 목록 항목에도 재사용. 동시에 S1의 `<h2>{asset.name}</h2>`에 `truncate` 클래스를 추가.

## 반영하지 않은 레퍼런스 패턴 (이유)

- **카카오페이의 "미정산 알림 자동 재전송"**: 알림을 보내려면 서버·푸시 인프라가 필요해 `CLAUDE.md`의 "복잡한 인증·외부 API 통합 금지" 경계를 벗어난다. 대신 앱을 다시 열었을 때 설정 탭 통계 카드에 "정산 대기 중 N건"처럼 로컬 데이터만으로 보여주는 정도가 이 프로젝트 범위에 맞다.
- **카카오페이의 "사다리 타기"(랜덤 분배), 최대 5차 다중 정산**: 재미 요소·부가 기능으로 이번 MVP의 핵심 문제(정산 정확성)와 무관해 제외.
- **Splitwise의 "그룹원 누구나 편집 가능" 무권한 철학**: 여러 명이 각자 기기에서 동시 접속하는 멀티유저 전제라서, 로컬 단일 기기·단일 관리자 구조인 우리몫에는 적용 대상 자체가 아님.

## 결론

세 서비스가 공통으로 하는 것은 "틀린 상태를 아예 만들 수 없게 막거나(토스), 틀린 상태를 실시간으로 보여주며 다음 단계로 못 넘어가게 막는(Splitwise·카카오페이)" 것이다. 우리몫의 계산 로직 자체는 정확하지만(정산 합계 검증·반올림 보정 등은 이미 꼼꼼하게 되어 있음), "언제 사용자를 막을지"에 대한 기준이 화면마다 흩어져 있다는 것이 이번 조사의 핵심이다. 1·2번만 먼저 반영해도 직전 자가검진에서 발견한 가장 심각한 문제(음수 지분 저장, 검증 기준 불일치)가 해결된다.
